## 1. What the ticket asks for

> As an event marketer, I want a single global configurator for shared Tier 1 session card settings so that track icon/color mapping, booking rules, and featured session flags are set once and consumed consistently by any surface that needs them (Session Guide today, other areas in the future).

Three config items in this release:
1. **Primary Digital Agenda Track icons/colors** — icon + color per track.
2. **Allow double booking** — toggle controlling whether a user can schedule overlapping sessions.
3. **Featured sessions** — per event day, and separately for the post-event/on-demand period.

The ticket explicitly scopes this to the **authoring surface only**; the consuming logic (how Session Guide's cards/badges/swimlanes read and render these values) is MWPW-200314's job, not this ticket's. The ticket also leaves two things unanswered: where the authoring UI lives, and what "global" means (scope granularity). Both were resolved with Daniel before writing this plan — see §2.

## 2. Decisions made against the raw ticket (recorded here, not guessed)

These are corrections/clarifications to the literal ticket text, confirmed directly rather than assumed — same practice as the session-guide-configurator ticket review (see `[[feedback-review-pm-tickets-together]]`).

1. **"Global" = per-event, not site-wide.** One config per Event ID, applied consistently across every block/surface on that event's pages — not a single org-wide singleton. Forced by the featured-sessions requirement: a session ID only exists within its own event's catalog (`fetchSessions(eventId)`), so a true site-wide config can't hold that field. Track-icon/color and allow-double-booking are "global" only in the sense of one setting per event reused by every consuming surface, matching how `track-icon-config` already works today.
2. **Storage = a single DA sheet acting as a config library, not the event page's own metadata (2026-07-21 revision, replaces the original decision).** The app no longer reads/writes an event page's DA source at all. Instead it's plain sheet CRUD against one shared sheet: one row per Event ID, holding that event's `tier-1-event-config` JSON as a cell value (plus a human-readable label for browsing — see §4). **The author copies the resulting JSON out of the app and pastes it into their event page's own metadata table by hand.** This is deliberate, not a shortcut: the whole point is that the sheet becomes a running library of past configs an author can reopen, duplicate, and tweak for a new event, rather than starting from a blank form every time. The event page's metadata still ends up holding the same `tier-1-event-config` key (see §4/consuming-side notes) — only *how it gets there* changed, from app-driven DOM-mutation to author-driven copy/paste.
3. **Single combined JSON value per row, not one column per setting.** One sheet cell holds one JSON object for all Tier 1 settings — see §4. Adding a 4th config item later means a new field on that same object, not a new column or a new metadata row on the page.
4. **This supersedes the old unticketed "Page Configurator" idea.** Before this ticket existed, there was a speculative, unticketed plan (`[[project-page-configurator]]`) for a DA app that edits an event page's page-wide meta tags in place via DOM-mutation read-modify-write. This app is explicitly **not** that anymore as of the storage revision above — it never touches a page doc — but it still retires that old idea's reason for existing (ticketed, real authoring surface for these page-metadata values), so the old `event-libs/page-configurator/` placeholder directory remains retired in favor of this one.
5. **Renamed "Global Configurator" → "Tier 1 Event Configurator."** Same tool, same scope as decided above — just a clearer name, since "global" was misleading once scope was settled as per-event rather than site-wide.

## 3. Precedent: Schedule Maker DA app

Two PRs establish the pattern for a DA-hosted app in this ecosystem:
- [da-events#37](https://github.com/adobecom/da-events/pull/37) — the **loader**. A single static file, `tools/da-apps/schedule-maker.html`, that mounts the real app via ES module import from event-libs, branch-driven by `context.ref` from the DA SDK handshake (`main`/`stage`/`dev`/any feature branch pushed to both repos, default `main`). No app code lives in da-events.
- [event-libs#185](https://github.com/adobecom/event-libs/pull/185) — the **app**, at `event-libs/schedule-maker/`. Preact + HTM + Spectrum, no build step. DA-native auth via the DA SDK's `org`/`repo`/token context (a `403` renders "no access" instead of a broken UI). File shape: `ScheduleMaker.js` (root), `components/`, `context/` (`DAContext.js`, `NavigationContext.js`, ...), `scripts/da-controller.js` (DA admin API calls), `constants.js`, `utils.js`, `htm-wrapper.js`, `README.md`.

Schedule Maker's **storage model pivoted twice** and both halves are relevant precedent, for different reasons:
- Its **original** design: sheet-CRUD (`readSheet`/`writeSheet`/`mutateSheet`) with ETag optimistic locking against DA's admin API, folder-scoped via a folder-path browser modal.
- Its **later, shipped** design: link-first — the entire payload lives in the share URL, no server-side storage at all.

**This app now follows the original design directly (2026-07-21 revision).** One shared sheet, `readSheet`/`writeSheet`/`mutateSheet`-style CRUD, ETag optimistic locking on write. The one difference from Schedule Maker's folder-scoped original: there's no folder picker — it's a single fixed sheet (one row per Event ID), not one sheet per folder. Everything else — read-modify-write via `mutateSheet` to avoid clobbering other rows on save, ETag conflict detection, real persisted state instead of link-first — carries over unchanged. (The earlier draft of this plan had it doing DOM-mutation against each event page's own doc instead; that's dropped now that storage moved to a sheet — see §2.)

**Concrete implementation precedent found 2026-07-22:** the *original*, pre-pivot Schedule Maker `da-controller.js` still exists in git history (`event-libs` commit `7fd24c5`, before the link-first rewrite in `f492d81`) with a working `readSheet`/`writeSheet`/`mutateSheet` trio — real code to port/adapt, not just a description:
- `readSheet(org, repo, path)` → `GET /source/{org}/{repo}{path}` via `admin.da.live`; DA's admin API returns `{ ":type":"sheet", "data":[...] }` for a `.json` sheet doc; returns `{ ok, data: rows, etag }`.
- `writeSheet(org, repo, path, rows, { etag, create })` → `POST` the full sheet back as `{ ':type':'sheet', ':sheetname':'data', total, limit, offset, data }` via `FormData`; `If-Match: <etag>` for a normal conditional write, `If-None-Match: *` when `create: true` (first write); a `412` response means a concurrent write landed first.
- `mutateSheet(org, repo, path, mutate)` → read-modify-write loop: read with etag, apply `mutate(rows)`, write conditionally, and on `412` re-read and retry (bounded, `MAX_WRITE_RETRIES = 4`) rather than clobbering a concurrent edit. This is exactly the row-level conflict handling §7's test plan calls for.

Port this trio for the new app rather than reimplementing sheet CRUD from scratch.

**Second precedent, found 2026-07-22: EMC (Event Management Console, `/Users/doliva/code/EMC`)** — a separate, already-shipped Adobe internal admin console, not part of the event-libs/da-events family, but relevant for exactly one piece: it already solves "browse/search the full ESP events catalog client-side" in production, via `ApiService.getEventsList()`'s `fetchAllPages()` helper (`web-src/src/services/api.ts:691,958`). See §5 for the full writeup and our own adjustments (date floor, cache TTL) before porting it.

## 4. Data model — the config library sheet + the page metadata it produces

**Two distinct artifacts now (2026-07-21 revision) — don't conflate them:**
1. **The sheet** — this app's actual storage layer. One shared DA sheet, one row per Event ID, acting as a browsable/searchable library of every config ever authored.
2. **The page metadata value** — what an author pastes, by hand, into their event page's own metadata table. Same JSON shape as before; this app just no longer writes it there itself.

**Sheet row shape (proposed):**

| Column | Contents |
|---|---|
| `Event ID` | Row key. Same Event ID used everywhere else (`fetchSessions(eventId)`, page's own `event-id` metadata). |
| `Event Title` | Human-readable label so authors can browse/search the library instead of hunting by ID alone. |
| `Config` | The JSON blob below, stringified — this is the exact value the author copies and pastes into their page's `tier-1-event-config` metadata row. |
| `Updated` | Timestamp, for sorting "recently edited" configs when browsing. |

**The `Config` JSON shape:**

```json
{
  "eventId": "...",
  "eventTitle": "...",
  "updated": "2026-07-22T21:30:00.000Z",
  "trackIcons": {
    "Track Name": { "icon": "icon-slug", "color": "#RRGGBB" },
    ...
  },
  "allowDoubleBooking": true,
  "featuredSessions": ["sessionId1", "sessionId2", "sessionId3", ...]
}
```

**`eventId`/`eventTitle`/`updated` are now duplicated inside `Config` itself, not just sheet columns (2026-07-22, per Daniel) — deliberate, not redundant.** The sheet columns exist for the library's own list/search/sort UI (cheap to read without parsing every row's JSON); the same three values are *also* embedded in the pasted `Config` blob so that once it lands in a page's `tier-1-event-config` metadata, there's enough self-describing information to verify it actually belongs there — e.g. a human glancing at the page's raw metadata table can confirm the `eventTitle` matches, and consuming code (MWPW-200314) can cross-check `tier-1-event-config.eventId` against the page's own `event-id` metadata and warn on a mismatch, catching a copy-paste mistake (pasting the wrong event's config onto a page) that this manual hand-off workflow makes possible. All three are app-populated, not author-typed: `eventId`/`eventTitle` come from the event picker's selection (1d), `updated` is set at save time.

**`featuredSessions` simplified to a single flat array (2026-07-22, per Daniel) — no `duringEvent`/`postEvent` split.** One authored list of session IDs, consumed independently by whichever view is showing at the time: `LiveUpcomingView` filters it down to whatever's relevant for the active day (existing `getFeaturedSessions` behavior), `OnDemandView` filters it down to whatever's still relevant post-event, with no day-scoping. A session doesn't need to be authored twice to be "featured" in both places — same list, two views each applying their own natural filter. See consuming-side notes below for what this changes on the reading side.

Adding a 4th config item later (ticket says more may come) means adding a new top-level field to this same object, not a new column or a new page-metadata row — the app, the sheet, and the consuming reader all change in one place.

**Resolved 2026-07-22 (per Daniel):** one config-library sheet **per content-repo** — da-events and each of its floodgate spaces (e.g. `da-events-fg-pink`) get their own separate library, matching Schedule Maker's existing repo-scoping (same loader file, `context`-derived `org`/`repo` at runtime). **Sheet doc path: `/tools/da-apps/tier-1-event-configurator/configs.json`**, resolved per-repo the same way the loader itself is (fixed, single path per repo — no per-folder scoping like Schedule Maker's original folder-picker, since each repo gets one library, not one per folder) — naming follows the real precedent found in §3 (`schedules-active.json`-style flat `.json` sheet docs).

**Consuming-side changes this forces (MWPW-200314's territory, explicitly in scope per Daniel) — unchanged by the storage revision, since the page still ends up holding the same key, just pasted in by hand instead of written by the app:**
- **New opportunity (2026-07-22): self-verification against a mispasted config.** Now that `Config` carries its own `eventId`/`eventTitle`/`updated` (see above), the consuming side can cross-check `tier-1-event-config.eventId` against the page's own `event-id` metadata at read time and `window.lana?.log()` a warning on mismatch — catching the real failure mode this manual copy/paste hand-off invites (an author pastes the wrong event's config onto a page). Not required for this app to ship, but flag it to whoever picks up MWPW-200314 as a cheap, high-value addition once the field exists.
- **`track-icon-config` is retired as a standalone key.** `event-libs/v1/utils/track-icon-config.js` currently does `getMetadata('track-icon-config')` directly. It needs to instead read `tier-1-event-config` and pull out `.trackIcons`. **Backward-compat fallback needed:** some da-events pages already have a real, authored standalone `track-icon-config` key today (this shipped and was live-verified before this plan existed — see `[[project-track-icon-config-system]]`). `initTrackIconConfig()` should check `tier-1-event-config.trackIcons` first, fall back to the legacy standalone `track-icon-config` key if the new key is absent, then fall back to `DEFAULT_TRACK_ICON_CONFIG` as today — so already-authored pages don't regress before someone re-authors them through the new app. Drop the legacy fallback once no live pages depend on it.
- **`allowDoubleBooking` (new) — event-wide across Tier 1 surfaces, not a sessions-guide-specific setting (resolved 2026-07-22, per Daniel).** A user can schedule sessions from more than one block on an event page — not only sessions-guide — so a double-booking conflict can happen across blocks, not just within one block instance. That rules out treating sessions-guide's existing per-block `show-conflict-modal` table row (`parse-config.js:27`) as a competing authority to "win" against the page-level setting: it's **retired/superseded, not kept as a per-block override**. `session-actions.js:scheduleAction`'s `showConflictModal` param should be driven by one shared, page-level read of `tier-1-event-config.allowDoubleBooking` — any Tier 1 block capable of scheduling a session reads the same value, the same way `getTrackIcon()` is one shared read today. Natural implementation: generalize `track-icon-config.js` into a broader page-metadata singleton for the whole `tier-1-event-config` object — one `getMetadata('tier-1-event-config')` read, exposing `getTrackIcon()`, `getAllowDoubleBooking()`, and (Phase 3) a featured-sessions getter, rather than three separate ad-hoc reads.
  - **`sessions-hub.js` explicitly out of scope, by tier boundary, not a gap (confirmed 2026-07-22, per Daniel).** `sessions-hub` has its own entirely independent scheduling/conflict flow (`handleSessionRegistration` → `findConflictingSession` → `openConflictModal`, vanilla DOM, no import from `session-actions.js`/`action-feedback.js` at all) that shows its conflict modal unconditionally with no gate today. This platform serves 3 event tiers; `sessions-hub` is mostly Tier 2/3, while this whole config system (and MWPW-200314) is specifically Tier 1 (MAX, Summit-scale events). So `sessions-hub` staying unwired is intentional, not an oversight — don't "fix" it as a side effect of Phase 2 without a separate decision to do so.
  - **Unverified assumption, carried to Phase 2:** no evidence in code that any live page currently authors `show-conflict-modal` as `true` (it only ever defaults `false`), so retiring it is likely low-risk — but real DA page content lives in DA's cloud store, not in either local git checkout, and couldn't be checked from this environment. Check via da.live/admin directly before actually removing the field in Phase 2.
- **`featuredSessions` — a single flat array of session IDs, no day-keying and (as of 2026-07-22) no during/post-event split either.** Today's `featured-sessions` metadata is already a flat array (`parse-config.js`, `session-filters.js:getFeaturedSessions`), which already resolves to "featured for the active day" as a side effect of `sessionsForDay` filtering — day is derived from each session's own start time plus the viewer's local timezone at render time, not something the config needs to pre-bucket (per Daniel, 2026-07-21: don't add a `days` grouping, the existing day-intersection logic already handles it for free). An earlier draft of this plan added a separate `postEvent` array for the ticket's "featured... separately for the post-event/on-demand period" ask; Daniel simplified that away too (2026-07-22) — **one array, consumed independently by each view** (`LiveUpcomingView` filters it by active day, `OnDemandView` will filter it with no day-scoping) rather than two authored lists. Still not fully final on the consuming-code details — surface the specifics (see the two real gaps below) to whoever picks up MWPW-200314 before building this app's featured-sessions step, so authoring and consuming shapes are designed together.
  - **Two real gaps found reviewing Phase 3, 2026-07-22 — bigger than "reuse existing code" — both still apply after simplifying to a single array (same underlying functions, just one shared list instead of two authored ones):**
    1. **Order isn't actually preserved by `getFeaturedSessions` today.** It does `daySessions.filter((s) => idSet.has(s.id)).slice(0, 3)` — that preserves the *catalog's* order, not the authored `featuredSessions` order. So §5's "the order the author picks/reorders sessions in is the display order" doesn't hold against the real function as it stands; it needs a small fix (map over the array in order, look up each session, then slice) before the reorderable picker UI actually does anything visible.
    2. **`OnDemandView.js` has no UI surface to land a featured section in at all, not just a missing data read.** Today it's just `onDemandSessions()` → `groupByTrack()` → a flat per-track list — no featured carousel, unlike `LiveUpcomingView.js`'s `<Carousel variant="featured">` section. And `getFeaturedSessions` itself can't be reused as-is here regardless of the order fix — it hardcodes day-scoping (`sessionsForDay(sessions, activeDay, userTz)`) via a required `activeDay` param, which doesn't apply post-event (`OnDemandView.js` has no `activeDay` concept at all). Needs a new, simpler function reading the **same** `featuredSessions` array (ID-membership only, authored order, no day-filtering) plus a new featured-carousel section added to `OnDemandView.js` mirroring `LiveUpcomingView`'s pattern — real UI work, not just wiring an existing read. One list, two independent consumers.

## 5. App shape

- **Loader:** `tools/da-apps/tier-1-event-configurator.html` in da-events, same shape as `schedule-maker.html` — imports `https://{ref}--event-libs--adobecom.aem.live/event-libs/tier-1-event-configurator/tier-1-event-configurator.{js,css}`, `context.ref`-driven branch selection, no `?eventlibs=` override (same reasoning as Schedule Maker: query params don't reliably reach the da.live iframe).
- **App:** `event-libs/tier-1-event-configurator/` — Preact + HTM + Spectrum, no build step.
- **Entry flow.** Landing view is the **config library**: a searchable/sortable list of existing sheet rows (by Event ID or title), each row offering **Edit**, **Duplicate → new Event ID** (the "remember previous config values and reuse them for other events" workflow Daniel asked for), or **Delete** (added 2026-07-22, Phase 4 — see below), plus a **New config** action. Both **Duplicate** and **New config** pick the target Event ID via the same ESP event picker (1d) — both need the same existing-row dedup check (Phase 4) before writing, since either flow could land on an Event ID that already has a config.
- **New config flow (2026-07-22 addition, per Daniel):** rather than typing a bare Event ID from memory, **New config** opens an **ESP event picker** — calls ESP's real `GET /v1/events` list endpoint (`events-service-platform` repo, `src/routes/events/read.js:74`; no IMS token needed, gateway API key only) to show real, selectable events. Selecting one fetches that event's sessions via the existing `fetchSessions(eventId)` abstraction (`event-libs/v1/services/sessions/sessions-api.js`, calling ESP's `GET /v1/events/:eventId/session-catalog` — confirmed correct and current, see below) — reused as-is rather than the new app duplicating a raw ESP call itself. That session payload feeds **both** the track-icon step and the featured-sessions step below, so it's fetched once, early, not deferred to the featured-sessions step alone.
- **Read:** `readSheet()` the single config-library sheet, list/search rows client-side. Opening a row loads its `Config` JSON into the 3 form sections. Track-icon section pre-populates its list from the **real tracks present in the fetched session list** (each mapped session already carries a singular `track` field — see open item below) rather than blindly showing all of `DEFAULT_TRACK_ICON_CONFIG`; any track with no authored icon/color yet still falls back to that default map for a sane starting icon/color, matching `track-icon-config.js`'s own gap-filling behavior.
- **Featured-sessions step:** uses the same already-fetched session list (no second fetch). **One picker, one flat `featuredSessions` array** (2026-07-22 simplification, per Daniel — no more separate during-event/post-event pickers), drawing from the full catalog. No day-tab grouping in either the stored schema or the picker UI (see §4). **Sort/display order** falls directly out of the array-shaped schema — it's an ordered list, so the order the author picks/reorders sessions in *is* the display order (once the consuming-side order fix in §4 lands); no extra schema field needed, just a reorderable picker UI (Schedule Maker's drag-to-reorder block precedent, `event-libs/schedule-maker/components/editor/BlockEditor.js`, is the closest reusable interaction pattern for this).
- **Write:** `mutateSheet()`-style read-modify-write — fetch the current sheet, update/insert only the one row being edited, write the whole sheet back with ETag optimistic locking (reject/re-fetch on conflict rather than silently clobbering another author's row saved in the meantime). Before serializing `Config`, stamp `eventId`/`eventTitle` from the picker's selection (1d) and `updated` to the current save time — app-populated, never author-editable fields.
- **Hand-off step: "Copy config."** After saving a row, the app shows the finalized `Config` JSON in a copy-ready block (or a dedicated "Copy config" button from the library list without even opening the editor) — this is the value the author pastes into their event page's own `tier-1-event-config` metadata row in DA. The app itself never touches that page.

**Open items from checking the real ESP repo (`/Users/doliva/code/events-service-platform`), 2026-07-22:**
- **Events-list picker — upgraded 2026-07-22 from "accept the limitation" to a real full-catalog search, following a proven precedent from EMC (Event Management Console, `/Users/doliva/code/EMC`).** `GET /v1/events` still only implements `page-size`/`next-page-token`/`from-date` server-side — no name/city/series/topic filtering, despite those params being documented in ESP's OpenAPI spec as "Coming soon." But EMC (a separate, real, already-shipped Adobe internal admin console) solves this exact gap in production today: `ApiService.getEventsList()` (`web-src/src/services/api.ts:958`) recursively pages through **all** of `GET /v1/events` via a generic `fetchAllPages()` helper (walks `next-page-token` until exhausted, `maxPages` safety cap), concatenates every page into one in-memory array, then does real client-side filtering/search on top (`EventsDashboard.tsx`: structured filters on `seriesId`/`creator`/`published`/`cloudType`/`defaultLocale`, plus substring search across `['eventName', 'eventType', 'cloudType', 'hostEmail', 'seriesId']`). This is real, running code — not a proposal — so we're adopting the same shape for our own picker rather than accepting "browse one page, filter within it only."
  - **Correction to an earlier finding:** `published` **is** a plain, always-present `boolean` field directly on the ESP event object (confirmed in `events-service-platform`'s own `openapi.json:15976`, and used directly by EMC with no special access). The earlier claim that "there's no simple published/draft boolean" was wrong — that must have conflated it with a separate, partly-deprecated `PublishingProfile` assignment concept that also exists but isn't needed here. Our picker can filter to published-only (or offer a published/draft toggle) using this field directly.
  - **Correction (2026-07-22, per Daniel — real curl test): the "auth is a non-issue" finding above was wrong.** The route-level code check was accurate (no auth logic in `read.js` itself) but incomplete — it missed that the **API Gateway in front of ESP enforces a real IMS Bearer token regardless of what the Express route checks**, confirmed by a working `curl` against `wcms-events-service-platform-deploy-ethos102-stage-caff5f.stage.cloud.adobe.io/v1/events` that 401s without `Authorization` and succeeds with one (a token issued to EMC's own `client_id: acom_event_mgmt_console`). So EMC's "always attach a real IMS token" isn't just its own convention — it's load-bearing. Unlike a normal Milo page, this app has **no IMS token source at all**: it's a standalone DA app with no `window.adobeIMS`, no Milo bootstrap. Fix landed 2026-07-22: `esp-controller.js` gained a `setEspAuthToken(token)` override (checked before `window.adobeIMS` in `constructRequestOptions`, so existing Milo-page callers are unaffected), and `DAContext.js` calls it with the DA SDK's own token as a best-effort Authorization Bearer. **Resolved 2026-07-22, live-tested by Daniel: reusing DA's token does NOT work.** With the real `?ref=local` DA-proxied flow and a real DA session token wired through `setEspAuthToken()`, the gateway returned `401 ErrInvalidOauthToken` — a *specific* rejection (not a generic 401/missing-header error), confirming the Authorization header reached the gateway but DA's token isn't a valid IMS OAuth token from ESP's perspective (different issuer/audience/client than what the gateway expects). **This app needs its own real IMS login flow**, mirroring EMC's client-side IMS SDK integration, rather than reusing DA's token.

**Implemented 2026-07-22: `events-milo` client_id, riding the shared Adobe IMS SSO session.** Pulled the real DA SDK source (`da.live/nx/utils/sdk.js` → `daFetch.js` → `ims.js`) to understand the token DA hands us: `setImsDetails()` confirms it genuinely is a real Adobe IMS access token, just scoped to DA's own registered `client_id`/scope — not a fake or non-IMS credential, which is why the 401 was a specific `ErrInvalidOauthToken` rather than a generic auth failure. Since DA's own login and Milo's login both ride the same underlying Adobe IMS SSO session, this app now bootstraps **its own** IMS session client-side (`tier-1-event-configurator/scripts/ims-controller.js`), using `client_id: 'events-milo'` — the exact client real production event-libs Milo pages already use successfully for `getEvent`/`getSessions`/etc., so it's already allow-listed by ESP's gateway. Mechanism: `window.adobeid` + `https://auth.services.adobe.com/imslib/imslib.min.js`, same imslib Milo and DA's own SDK both use — bounded at a 5s timeout, never rejects (a slow/blocked IMS load degrades to no `Authorization` header rather than blocking the app). `esp-controller.js`'s `constructRequestOptions` already reads `window.adobeIMS?.getAccessToken()?.token` as its primary path, so no changes needed there once `window.adobeIMS` exists — `listEvents`/`getEventSessionCatalog` were flipped back to the default `waitForIMS: true` now that there's a real session to wait for. **Verified in a sandboxed test browser (no real Adobe SSO session) that this degrades gracefully** — IMS resolves anonymous, the ESP request correctly goes out with no `Authorization` header rather than a broken one.

**Bug found and fixed 2026-07-22, live-tested by Daniel: IMS environment was wrongly coupled to the ESP backend environment.** First real live test (via the actual `?ref=local` DA flow, real signed-in session) came back with no `Authorization` header at all, and IMS's own `ims/check/v6/token` endpoint on `stg1` returned `invalid_credentials`. `ims-controller.js` originally derived the IMS `environment` param from `getEventServiceEnv()` (the loader's `event-service-env` meta tag, at the time set to `local` → `stg1`) — but IMS environment is about where the *user's* real SSO session lives, completely independent of which ESP backend the app happens to be querying data from. 2. **Multiple independent internal sources (Slack threads + a CGW FAQ page) confirmed `allowedClientIDs` — CGW's client-id allow-list feature — only ever applies to *service* tokens, never *user* tokens.** ("CGW does not perform client ID validation for user tokens.")
